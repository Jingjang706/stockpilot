# Engineering decisions and assumptions

Where the brief was ambiguous, these are the choices made (and why).

| Area | Decision | Reason |
|---|---|---|
| Roles | `users.role` is a constrained column (`ADMIN`/`MANAGER`/`CASHIER`) rather than a `roles` table | Three fixed roles; a join table would add complexity without value. A `roles`/`permissions` table is listed under future work. |
| Stock integrity | `inventory.quantity` has `CHECK (quantity >= 0)`; every change goes through `InventoryService.applyChange` with a row lock (`SELECT ... FOR UPDATE`) | Two layers: the service gives clean errors, the constraint makes negative stock impossible even through a bug. **Negative stock is never allowed**; no override workflow was built. |
| Audit of stock | `stock_movements` is append-only; each row stores the resulting balance (`quantity_after`) | Inventory history can be reconstructed and reconciled. |
| Sale atomicity | One `@Transactional` method writes sale, items, payment and movements. Products are locked in ascending id order | A failure on any line rolls back everything; consistent lock order prevents deadlocks. |
| Money | `NUMERIC(12,2)` in the DB, `BigDecimal` with `HALF_UP` in Java, never floating point on the server | Exact cents. The browser only previews totals; the server recomputes everything from database prices. |
| Prices at sale time | Sale lines snapshot name, SKU, unit price and **unit cost** | Later price changes never rewrite history, and gross profit stays correct. |
| Revenue / COGS / profit | Revenue = totals of `COMPLETED` sales; COGS = snapshotted cost x quantity; gross profit = revenue - COGS. Voided and refunded sales are excluded and reported separately | The brief asks for these to be clearly distinguished. |
| Discounts | Fixed amount per sale. Cashiers up to 5% of the subtotal; managers/admins up to 100% | "Appropriate permissions". The limit lives in one constant (`SaleCalculator`). |
| Void vs refund | Void = same business day only (fixing a mistake). Refund = any time. Both are **full** reversals, need a reason, restore stock and are audited. Partial refunds are not supported | Keeps the stock/finance invariants simple and verifiable. |
| Purchase flow | `PENDING -> APPROVED -> RECEIVED`, or `CANCELLED` before receipt. Receiving is all-or-nothing and updates the product's cost price to the latest purchase cost ("last cost") | Partial receipts are future work. |
| Cashier visibility | Cashiers never receive cost prices or COGS in API responses, see only their own sales, and cannot see archived products | Enforced in the service layer, not just hidden in the UI. |
| Passwords | BCrypt (strength 10). Admins never choose passwords: the server generates a one-time temporary password, shown once, and `must_change_password` blocks every API call except change-password/me/logout until it is changed | "Secure reset process" without email infrastructure. Email-link reset is future work. |
| Tokens | Stateless JWT (HS256), 8 h default. The user row is re-checked on **every** request so deactivation and role changes apply immediately. The frontend keeps the token in `sessionStorage` | Trade-off: no server-side revocation list; a stolen token is valid until expiry. Refresh tokens / httpOnly cookies are future work. |
| Login errors | Same message for unknown user and wrong password; failed attempts are audited | Prevents username enumeration. Account lock-out / rate limiting is future work. |
| Time zone | All timestamps are `timestamptz` (UTC). "Today", daily/weekly/monthly buckets and receipt dates use `APP_TIMEZONE` (default UTC) | Reports must not shift around midnight; set it to the shop's zone in production. |
| CSV export | Generated in the browser from the report JSON, with formula-injection protection | No extra endpoints; same numbers as the screen. |
| Product images | Stored as a URL (`image_url`) | File upload/storage is future work. |
| Customers | The `customers` table exists (listed in the brief) and `sales.customer_id` is nullable, but no API/UI uses it yet | Documented rather than shipped as a fake feature. |
| Demo data | Lives in a separate Flyway location (`db/seed`) loaded only when `FLYWAY_LOCATIONS` includes it. Generated by `database/generate_demo_seed.py` | Production databases never receive demo users. Demo passwords are documented as demo-only. |
| Schema vs entities | `JPA_DDL_AUTO` defaults to `none` (Flyway owns the schema); the integration tests run with `validate` | Entity/schema drift fails the test suite. |
